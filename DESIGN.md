# CodeMaster design context

## Overview

Authenticated programming learning platform with school workspaces and a separate public practice area. Preserve the compact teaching/workspace layout established by the user: the statement and editor carry the content; no new hero cards, decorative banners, or large headings. Chinese and English UI use the existing locale provider; paid translations are versioned assistance, never an effect of switching UI language.

## Colors

Runtime owner: `apps/web/src/app/globals.css`; its `:root` / `.dark` semantic variables map through `@theme inline` to utility classes. Values above document the existing light theme; do not copy them into components or change global tokens for an isolated feature. Code theme tokens are independently owned by `student/editor-themes.ts`.

## Typography

Retain the existing system Chinese/Latin sans stack and monospace code stack. Body statements retain readable line height. No new fonts or packages.

## Layout

Keep controls compact, with wrapping header rows and min-width constraints. Long code scrolls inside its block. Theme controls sit above code and must not affect editor layout, stored drafts, requests, pricing, or assistance delivery.

## Elevation & Depth

Use existing surface/border/modal primitives; no new shadows or overlays for theme changes.

## Shapes

Reuse the existing half-rem base radius and component utility variants.

## Components

- `acsl/AcslPage` adds school-enabled ACSL practice to the student navigation. Its compact paper list and question rail reuse `WorkspaceFrame`, existing Button and native select/input controls, `LessonContent`, semantic tokens and the locale provider. Question content has an explicit English/Chinese control independent of interface language. Single and multiple choice use labeled native radio/checkbox groups with compact, baseline-aligned content. Each selection is saved with a server revision. Before the short section is submitted, the rail shows which questions have saved answers. Once all answers are saved, the shared confirmation dialog submits the short section for grading. The graded view locks the choices, shows the short-section score and individual verdicts, and lets students open explanations. Programming uses `ProblemWorkspace` through a school/paper/version adapter and returns to the selected short problem.

- The ACSL catalog groups papers by academic season, newest first, then the fixed Elementary / Junior / Intermediate / Senior division order and Contest 1–4. Native division, season and contest filters and the count of expanded seasons stay in the URL through paper and programming navigation. Older seasons open on request. Each row separates saved written answers or the submitted score from programming progress; written-only papers have no programming entry. Written prompts, actual answer choices and explanations use native Markdown and KaTeX. `acsl/AcslNativeDiagram` renders trees, circuits and graphs from bounded, validated SVG primitives; no raw SVG, HTML, scripts, external references or source-page crops are used for this presentation. Diagrams fit their natural width within the content pane; the shared Dialog provides local zoom without widening the page. Semantic ink and surface colors follow the current theme, while the limited named instructional colors retain their diagram meaning. `acsl/AcslRichContent` places a supplied diagram at a standalone `{{diagram:id}}` paragraph and appends unreferenced diagrams in source order. Option diagrams remain noninteractive inside native labels. Written explanations and their diagrams remain behind explicit disclosure after grading. The programming adapter reuses this renderer through the shared workspace’s optional statement presentation hook; judging is unchanged.

- ACSL stage feedback reuses the shared Dialog and compact result surfaces. A successful answer save that leaves the written section ready to submit arms one prompt after 1.2 seconds without further edits; it never submits automatically and focuses Continue checking first. Session memory is scoped to account, school, paper and written revision. Opening manual confirmation also consumes the prompt, while reopening a previously saved paper does not arm it. A successful written submission or a newly accepted formal programming submission opens `AcslStageResultDialog`; programming first refreshes the server paper state. The summary distinguishes Written section submitted, Programming passed and Paper completed, and totals only server-confirmed awarded points. Sample/custom AC and predicted rewards never establish completion. Reopening historic results does not automatically open a dialog; historic summaries remain available through an explicit action.

- `AcslReviewPanel` shows graded papers only, with the saved score, stage status, actual option content, the student's submitted choices and verdicts. All/incorrect filters stay in the URL; each View explanation action navigates to that question and explicitly requests its explanation. The list never preloads explanations, and the all-correct empty state offers a route back to all questions. Catalog rows link graded papers to Results and review and show Paper completed only when the written section is graded and any programming problem has a formal AC; written-only Elementary papers complete at grading regardless of score. Review and programming navigation preserve catalog filters, content language and the return question. This first stage adds workflow feedback and review, without claiming unified explanation depth or companion courses.

In the teacher problem editor, a Tutorial tab between Solution and hints and Versions and publication edits settings in place. Legacy problem bank shortcuts open that tab. Reference import appends an article without replacing existing approaches. All edits, including published primary text, remain drafts until review; student reading stays on the approved snapshot. ## Do's and Don'ts

ACSL teacher management (094, 2026-11-10): original-school teachers and administrators use `/teacher/acsl` and `/admin/acsl`; other schools use their scoped ACSL section. The shared catalog keeps season/division/round preferences. Teacher details show authorized bilingual answers without creating student work. Editing uses shared inputs, buttons and native rich-content preview; stable question/option structure and programming judge configuration are read-only. Saving requires a reason, preserves entered content on conflict and records a new written revision without changing historical grades or rewards. Question-content changes require pending students to reconfirm affected answers. Single-paper export opens a separate print view that fetches only its student or teacher projection; the student view never loads answer-bearing detail. PDF is saved with browser print using KaTeX and SVG on white pages, while complete JSON is explicitly marked as teacher material. All management access is enforced by current school permissions on the server.

Editor follow-up: Escape in the focused code input enables Vim normal mode through the existing settings owner. Normal/visual modes use a full character block with the covered glyph repainted in the theme background color; the block uses `--code-foreground`. Insert mode uses a 3px vertical bar. Forced colors use CanvasText/Canvas. A non-collapsed native text range measures the current character, with one cell for tabs/empty lines; local coordinates account for CSS zoom. The decorative cursor stays clipped to the code viewport and hides on blur or activity read-only state. `FormatCodeIcon` owns the user-selected text-align-start paths for both answer workspaces, with currentColor and the existing toolbar size.

Use existing tokens and sibling controls, not a rebrand. Do not preload or persist locked translations/answers; do not expose reference programs, hidden tests or private notes via ordinary question payloads. Do not reset code or dirty state on theme changes. Scope verification to the touched workflows and record unrelated pre-existing audit findings separately.
