# School-scoped identity activation

Activation claims an existing school directory identity. It is distinct from personal registration and from a membership invitation.

- `/activate` offers a **School / 学校** dropdown, followed by student/staff role, number, name and one-time activation code. No school is selected by default. Names use the selected UI language; duplicate names include the stable school code to disambiguate. Changing school clears the entered activation code. The verified step confirms the school name and identity before creating credentials.
- `GET /auth/activation-schools` is a public, read-only directory returning only `id`, `slug`, `name`, `nameZh` and `nameEn`. It exposes no identity, roster, account or activation token data and grants no membership. The dropdown submits the selected stable `slug` to the existing claim checks; loading, retry and empty states cannot accidentally submit a different school.
- A school administrator issues an activation code from the unlinked identity's row. The response displays the school name, school code and activation code once; copying includes all required identity details. Issuing a replacement invalidates the previous code. Codes expire after seven days.
- A school code does not enumerate identities. Verification discloses identity/class details only after the school, role, number, name and secret all match. Wrong school, unknown school, incorrect credentials, already claimed identity and invalid issuer receive the same claim failure.
- The global login uses a `personal` credential identity. The claim transaction creates the account and matching school membership, attaches the existing `school_identities.id`, consumes its token, creates an audit event and opens a session atomically. It grants no original-school role or platform privilege. Existing school rosters continue to point to the same school identity.
- Original-school activation keeps its stable `identities.id`, historical links and existing role behavior. New UI requests explicitly send `schoolSlug`. For old client compatibility, omission is confined to `legacy-school` and verified against `legacy_school_identity_ownership`; it never searches another school's directory.
- Existing signed-in accounts can still join through a membership invitation and be linked to a matching school directory identity by their administrator. Activation creates a new login; it does not silently merge existing accounts.

Migration `065_school_identity_activation.sql` adds the school/identity-scoped token table. Run the migration and runtime grants as the migration owner. No existing identity, credential, roster, grade or scholarship record is rewritten. The application can issue/consume tokens; the judge worker has no token-table access. Activation secrets are stored hashed and excluded from directory responses and audit records.

Validation uses `apps/api/test/school-activation-http.integration.test.mjs` with a disposable localhost QA database and the real Nest transport under `campus_app`. It covers the public directory's exact safe fields, identical student and staff numbers/names in different schools, wrong-school rejection, authorization and CSRF, concurrent single-use registration, roster preservation, expiry/reissue, issuer revocation, original-school compatibility, absence of cross-school grants and worker isolation. Frontend validation requires an explicit school selection. Test credentials are generated per run and are not stored in source.
