# tx99 / ali99 共用写入主库（2026-10-27）

## 授权和结果

用户明确要求两个站点同时供学生使用，采用一个写入主数据库，并保留两边已有学生记录和 Luq 数据。本次取代 [D57 独立副本](campus-judge-design-summary.md#decision-d57) 的运行拓扑，保留其实施历史和备份。

- 主站：[cmoj.space](https://cmoj.space)，运行于 tx99。
- 第二入口：[ali99 HTTPS 8443](https://139.196.155.201:8443)，保留原内部 CA 和 IP 证书。
- tx99 的 `campus` 是唯一在线生产数据库；ali99 的 API、worker 通过受限加密 SSH 隧道访问它。
- 学生身份、账号、班级、课程关联、提交、成绩、活动、余额、追加式 Luq 流水、权益和辅助提供记录使用同一份事务数据。无需定时复制，也不提供双主冲突合并。
- 未导入本地 3000 的学生数据库；本地体验部署不变。部署实施阶段未提交或推送 Git，未修改 rslab；后续源码归档授权见文末。

## 两边原有数据的保留

先为两边分别创建一致性数据库备份、完整逐行快照和逐表指纹，并在独立 QA 库恢复。以 ali99 最初从 tx99 复制时的快照为共同基线，进行三方比较；切换时暂停两个公网入口和 API/web，排空普通题及 Paper 4 队列，再停止 worker 和取得最终快照。

ali99 相比共同基线新增 1 个账号、18 次提交、关联队列/判题运行、一个已发布题目版本及用例、2 笔首次 AC Luq 奖励（合计 8 Luq）、积分、会话和审计记录。主库没有与这些学生行为冲突的新增记录。两个站点各自发布的同一道题实际正文、参考代码、元数据和用例相同，仅发布时间/审核时间不同：保留两个版本及各自提交关联，当前版本指针沿用 tx99。

一次性合并经过 QA 演练后在维护事务中执行：

- 使用表级变化白名单、主库原始记录集合校验、行/表锁、事务锁和唯一导入审计标记；发现非预期修改、删除或键冲突即终止。
- 学生、提交、运行、版本、Luq 流水和奖励来源保留原稳定 ID。12 条审计事件遇到序列编号重叠，分配新编号，并在导入审计中保存旧新映射。
- 仅在维护事务内暂时停用提交的业务触发器，再恢复原状态，避免历史提交再次触发奖励或重算辅助快照；外键仍生效。分阶段恢复版本发布时间、用例和提交运行关联以满足约束。
- 既有 Luq 流水不修改、不删除。按已核实的新流水增量增加相应余额，不用 ali99 的整行余额覆盖主库；原奖励时间、金额和余额流水保留。
- 消费、退款、首次 AC 和活动奖励仍使用现有唯一约束及事务规则；没有重发初始助学金或历史奖励。

切换前后逐行保留证明：**主库 8,632 条原记录和 ali99 新增的 90 条关联记录全部保留，新增 8 Luq 完整保留**。账号最后登录时间、已消费激活码及经核实的余额增量按合并规则更新。两边既有密码、停用状态、课程与章节关联没有重置。私有 SQL、源快照和证明只保存在受保护的备份目录，不进入源仓库，也不可重复执行。

## 网络、角色和运行边界

```text
cmoj.space -> tx99 gateway/web/API --- campus_app ----------+
                        worker ----- campus_worker --------+--> tx99 PostgreSQL campus
                                                          |
ali99:8443 -> gateway/web/API --- campus_ali_app -- SSH -----+
                        worker - campus_ali_worker --------+

每台 worker -> 本机隔离 go-judge；执行器没有数据库连接或 Docker socket
```

tx99 数据库继续在内部 Docker business 网络，没有发布 PostgreSQL 端口。宿主 `campus-primary-db.socket` 只监听 `127.0.0.1:15432`；socket proxy 在建立连接时查找当前数据库容器地址。每 15 秒检查一次地址，容器地址变化时重启代理。socket、watch timer 和代理失败重启配置已启用。

ali99 使用独立非 root 隧道用户和专用密钥，严格固定 tx99 SSH 主机密钥。tx99 的 SSH key 限制 ali99 来源、唯一转发目的地 `127.0.0.1:15432`，并禁用 shell、PTY、其他端口转发、远程监听、agent 和 X11。没有借用管理员 SSH key。

ali99 隧道只在本机 business bridge 的 `172.18.0.1:15432` 监听。持久化防火墙只接受该业务桥和 loopback，拒绝 edge/execution 网络；隧道启动依赖防火墙。桥网段、接口或容器网络重建后，必须重新核验并更新这些宿主配置，不能直接套用固定地址。

ali99 的 API 使用非超级用户 `campus_ali_app`，继承 `campus_app`；worker 使用独立的 `campus_ali_worker`，继承 `campus_worker`。新登录角色各限制 10 个连接，无建库、建角色、复制或超级用户能力。API 不得直接改余额/流水；worker 不得读取或写入 Luq 内容和流水。执行器网络及凭据边界保持不变。

两个 worker 的节点 ID 不同，继续使用数据库任务租约、共享节点容量、行锁和 fencing，避免重复占用任务；奖励和扣费的幂等性由原数据库事务及唯一约束保证。

## 断线、重启与迁移

- ali99 本地原数据库已停止，容器、原卷及独立快照保留。Compose 把本地 db/migrate 置于 `local-archive-only` profile，默认启动不恢复它，ali99 迁移命令明确拒绝执行。
- 数据库版本迁移只在 tx99 执行一次。两站应用升级应保持 API/worker 与同一数据库结构兼容。
- 隧道异常时 ali99 的数据库请求失败，不连接旧副本。专用 systemd 服务自动重连；tx99 主站仍直接连接自己的数据库。
- 为处理连接空闲期间断线，`createPool` 增加受控的 `pg.Pool` error listener，让 pg 移除失效连接并在后续请求重连。日志仅含固定事件名和清理后的错误码，不包含凭据、SQL 或正文。没有自动重放未知结果的业务事务。
- 代码回滚也必须继续使用共享主库。不得把旧 ali99 卷重新作为在线回退数据库，否则会形成新的数据分叉。
- 此拓扑没有自动主库故障转移。tx99 数据库故障将影响两个入口；跨云延迟也会影响 ali99。需要恢复时以最新主库备份为准，先停止两个入口写入，再恢复/切换；旧副本不是当前数据副本。

部署模板和运维边界见 [deploy/shared-primary](../deploy/shared-primary/README.md)。真实数据库 URL、专用私钥、应用 session secret 和原卷凭据只在权限受限的私有配置内。

## 备份、审计与日常使用

两台服务器的受保护目录均为 `/srv/codemaster-oj-backups/shared-primary-20261027/`。保留各自 preflight、cutover 一致性备份和原部署配置；tx99 另有 `final-primary.dump`、包含新角色授权的私有 globals 备份；两台均有 `final-deployment.private.tar.gz`（私有环境、隧道/代理、防火墙及 systemd 配置）和 SHA256 清单。最终主库 dump 已在独立 QA 库实际恢复。部署材料与数据库备份另复制到本机 Git 忽略的 `.campus-local/deployments/shared-primary-20261027/`，校验哈希；不把学生信息和密钥加入公开文档或 Git。

仅需在两个站点分别登录，账号密码仍使用原值。业务数据直接共用，但浏览器草稿和登录不等同于数据库数据：

- 正式提交的代码、成绩、服务端保存的 Paper 4 作答、课程进度、Luq 余额及解锁权益跨入口一致。
- 普通题未提交草稿及语言选择仍按原设计保存在当前浏览器的 `sessionStorage`，不会跨域或跨标签页自动同步；编辑器本地设置也按浏览器保存。本次没有重建编辑器或改动这些草稿。
- 两站保留各自 Origin、Cookie 和 session secret，不能依赖一个站点的登录 cookie 在另一站自动登录。无公开跨域接口或共享凭据缓存。
- 应用镜像和原卷等静态资源仍需要同时部署；当前资源哈希一致，共享数据库不自动复制未来新增的构建文件。

没有新增定时数据库覆盖、双向 rsync、余额覆盖、学生记录重放或自动主库提升任务。
