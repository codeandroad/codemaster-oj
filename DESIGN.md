# CodeMaster design context

## Overview

Authenticated programming learning platform with school workspaces and a separate public practice area. Preserve the compact teaching/workspace layout established by the user: the statement and editor carry the content; no new hero cards, decorative banners, or large headings. Chinese and English UI use the existing locale provider; paid translations are versioned assistance, never an effect of switching UI language.

## Colors

Runtime owner: `apps/web/src/app/globals.css`; its `:root` / `.dark` semantic variables map through `@theme inline` to utility classes. Values above document the existing light theme; do not copy them into components or change global tokens for an isolated feature. Code theme tokens are independently owned by `student/editor-themes.ts`.

## Typography

Retain the existing system Chinese/Latin sans stack and monospace code stack. Body statements retain readable line height. No new fonts or packages.

## Layout

Keep controls compact, with wrapping header rows and min-width constraints. Long code scrolls inside its block. Theme controls sit above code and must not affect editor layout, stored drafts, requests, pricing, or assistance delivery.

## Elevation & Depth

Use existing surface/border/modal primitives; no new shadows or overlays for theme changes.

## Shapes

Reuse the existing half-rem base radius and component utility variants.

## Components

- When tutorial content is available, the problem workspace adds a Tutorial tab between Translation and Solution. Its lesson scrolls in the statement pane while the editor and test panels stay available. In the teacher problem editor, a Tutorial tab between Solution and hints and Versions and publication edits settings in place. Legacy problem bank shortcuts open that tab. Tutorial settings use a native select for the three sources, retain edits across tabs, and save independently of the problem draft.
- `WorkspaceFrame` owns the shared sidebar, brand, compact breadcrumb header, account area and responsive mobile navigation for platform administration, the existing school, new schools and free practice. It reuses the original layout and semantic tokens. A school workspace shows the current school's locale-specific name beneath `BrandLogo`: preferred language, then the other name, then the compatibility name. The brand area does not shrink, the school name wraps, and long navigation scrolls separately so the logo is not clipped. Platform and free practice show their own workspace labels. New schools reuse this shell and existing business components, but only expose implemented functions; visual reuse does not mean every legacy module has been migrated.
- `schools/SchoolsPage` resolves `/schools` against the account's current server memberships. New-school administrators and teachers have a Dashboard alongside their implemented teaching modules; students have Home, Problems, Courses, My classes and Submissions. Administrators additionally manage Identities, Members & invitations and Judge service. Selecting the original school forwards into its existing role-specific workspace and full business navigation. School settings are reached from personal settings, not a separate sidebar item; original-school member/identity management keeps its authoritative role model. Assignments, timed practice, Paper 4, school Scholarship, and reports are not yet migrated for new schools, so their sidebar is not claimed to be identical to the complete original-school navigation. Section content remounts per school; role-specific navigation comes from that school's current membership, not the account's original-school roles.
- `schools/JoinedSchoolSettings` owns school selection, default-school preferences and invitation joining inside personal settings. `AccountMenu` opens settings in the active platform, school or free-practice context; new-school settings links retain the current school ID. There is no permanent “Your schools” sidebar, switcher trigger or invitation form in the workspace chrome. School rows show membership roles and explicit Open/default actions; invitation entry opens only after the user presses its button. Codes stay masked in temporary component state and never enter URLs or persistent storage; newly issued invitations are retained in a school-keyed in-memory map until cleared or this page is left. Issuing disables school/section switching and sign-out until settled. Browser preference stores only the last school UUID per stable account ID, always revalidated against server memberships. Current context resolves each candidate independently: explicit school ID, browser current school, server default, then a valid fallback. Direct entry to original-school routes remembers that actual context. Another tab's preference change does not force navigation.
- `schools/SchoolAdministration` uses the original class-card / adjacent roster composition, compact Active/Archived controls, shared tables, native selects and Loading/Feedback primitives. Administrators manage school identities, classes and teacher assignments. Linked teachers can create classes and manage students only in their assigned classes; they cannot assign teachers. Students see their own active classes and a read-only classmate list with safe fields. Pickers distinguish records by number or username. Unlink, member removal and roster removal name the person, school and impact, with Cancel focused first. Archive/restore retains rosters and uses revision checks. Domain authority remains `docs/multischool-workspaces.md`.
- `schools/SchoolDashboard` provides school-scoped continuation, class/course/problem summaries and students' recent submissions using real authorized data. `SchoolSubmissions` shows only the signed-in account's formal school submissions; it does not render worker payloads or hidden tests. `SchoolPractice` uses compact bank/problem tables with search, status and actions. These components retain original workspace tokens and navigation patterns without pretending unavailable legacy modules exist.
- Profile and Settings are separate destinations in every account menu, including platform, new-school and personal accounts. `schools/PersonalWorkspaceProfile` reuses the original `ProfileEditor` for avatar, nickname, biography and account details; it does not append a second profile form to Settings. Settings owns appearance/language and joined schools/default school. Both destinations retain the current workspace sidebar and school context; a platform administrator need not join a school to edit their own profile.
- `schools/SchoolSettings` exposes Chinese and English school names in the school-details dialog opened from a personal-settings school row. Members can inspect their school and roles; only that school's administrator can edit its names. At least one name is required. Save carries the loaded revision; conflicts retain input and require refresh. Pending requests prevent duplicate submission/dismissal, and unsaved edits confirm before closing. Original-school administrators use their existing role authorization. Successful save refreshes the current-school label in both original and new-school workspaces.

- `SolutionContent` is the shared ordinary/Paper 4/teacher-preview code-theme renderer. It receives a body only after existing authorization/delivery or teacher preview; it never fetches, purchases, or stores assistance bodies. Default GitHub Dark; all presets come from `editor-themes.ts`.
- School class rows and roster headers expose an explicit administrator-only `Assign teacher` action. Both use the existing roster picker in a teacher-only variant, show account-link state and explain access for unlinked teachers; no new assignment or authorization model is introduced.
- `schools/SchoolIdentityImport` is the shared administrator import flow for the identity directory and class roster; assigned teachers use its student-only variant locked to their current class. It reuses the existing Modal, Button, paged table and native selects. A bounded preview distinguishes new, existing, duplicate, conflicting and invalid rows before confirmation. Changing the file, identity type or class invalidates the preview; pending mutations prevent duplicate submission and preserve the exact token for retry. Parsed names/numbers stay in component memory, never URLs or local storage. Imports do not create or link login accounts. Domain authority is the batch-import section of `docs/multischool-workspaces.md`.
- Theme selection uses a visible label and native select. Platform-owned popup behavior is intentional, consistent with the established Paper 4 selector; preserve keyboard selection, focus outline, and localized accessible name.
- `LuqAssistance` owns quote/confirmation/unlock/delivery and existing retry/status rules. `Modal`, `Button`, `CodeBlock`, `MathContent`, and `useLocale` remain canonical owners for their respective behavior. Existing domain/security decisions live in `docs/luq-system.md` and D47–D50 of the design summary.
- A theme change is local presentation state: no network mutation, no new delivery, no balance change. Data/content publication remains independently authorized and audited.

- `CodeEditor` remains the shared textarea/highlight editor for ordinary problems and Paper 4. The optional Vim keymap is owned by `student/editor-vim.ts`, selected in the existing native key-binding control, and persisted by `useWorkspaceSettings`. Standard remains the default. Mode/search feedback belongs in the existing status row; no new toolbar or modal. Keyboard handling consumes Vim Escape without closing workspace panels; native Tab still moves focus outside insert mode. Only content changes notify draft owners.
- Vim insert mode uses a compact list of local code suggestions anchored to the caret. It stays inside the code viewport and uses its theme tokens. Focus stays on the textarea while the list is open; moving through candidates does not edit the draft. The editor dismisses the list on blur, IME composition, read-only transitions, and leaving insert mode.

- `CopyCodeButton` adds the supplied copy glyph (`#030303`, 2.25 stroke) to existing editor toolbars. It copies the current buffer without editing it; success briefly becomes a check, and failures provide an accessible message. `ScholarshipIcon` retains the separate requested gold (`#EFBF04`). `SolvedStatus` sits at the statement's upper right and uses an authorized formal AC for the displayed version; sample runs never mark a question solved.
- `ProblemSubmissionsTable` replaces the answer workspace's My submissions tab with Submissions. The compact table shows the latest authorized formal submission per person. The server filters authorization first, groups by actor, then sorts by time/status/language/runtime/memory and paginates people. The current student has a tinted row, leading border and You badge. Solved still uses the authorized history, so a later WA does not erase an earlier formal AC. It exposes no other student's code, identity, hidden cases or private notes. Only the signed-in user's ordinary submission can link to its existing detail page. Unknown measurements show an em dash, not a fabricated zero. Exam results remain hidden until release; school and free-practice histories retain their distinct scopes. This is separate from the sidebar's personal submission history.
- `RunResultPanel` shows the server-authorized first wrong-answer case for the student's ordinary submission, using the existing input, output, expected result and diff blocks. In an active workspace, Use as custom input focuses the filled input field so the student can rerun it. The panel reads the same case data in submission history and respects the server's competition and result-release rules.
- `ScholarshipPopover` is the balance button in the original school, new-school and public workspaces. It opens up to five recent entries from the current wallet in place, with a compact balance trend and a separate link to the full ledger. It follows the adjacent notification panel's outside-click, Escape and viewport positioning behavior.
- The original school's assignment editor uses `ScholarshipIcon` for per-problem and on-time completion amounts. The problem table shows the cited version's difficulty label next to per-problem scholarship. Basic information places the completion amount next to the deadline, Problems links to that field, and Rules shares the existing eligibility controls. Preview and publish confirmation show both amounts separately. The completion rule saves with the draft and freezes on publication.
- The student home card, assignment list and assignment detail show a checked completion badge and green progress when every required problem has passed. The progress count includes credit from other entries and appears separately from the score and the count of problems submitted in the assignment. An archived assignment retains its completion badge. The home card links to the assignment detail when complete and offers to continue at the first unfinished problem when available.
- Avatar menus no longer duplicate Join a school; Settings → Schools remains the joining entry. Existing leaderboards add a Scholarship field controlled alongside other student-visible metrics. It is the current balance even for a historical ranking period; it neither creates a balance leaderboard nor changes the current tie-break or attempt-counting policy.

- Public authentication uses the existing system light palette from `globals.css :root`, with a light gray canvas, separate left brand introduction and right white login card, and solid school-blue primary actions. `auth/AuthShell` and `auth/auth-shell.module.css` are shared by login, password reset and every registration step. No `.dark` override, alternate palette, external font or gradient is applied; authenticated workspace themes remain independent. Public role introductions show only students and teachers; this is presentation, not authorization. The student summary is “课程学习、自由练习”. The public brand subtitle is “Coding, learning & practice” / “编程学习与实践”, with no school name. `AuthNotice` uses the same shell for session loading and connection failures on `/login`, `/register` and `/activate`.
- `ProductionLoginPage` keeps username credentials and administrator-issued reset, with explicit links for personal account creation, invitation joining and school identity activation. `/register` uses `PersonalRegisterPage` for display name, username, password/confirmation and optional email; it does not ask users to choose an authorized role. `/activate` keeps `ProductionRegisterPage` identity verification → account setup → completion for existing school activation codes. Both forms use the same input/button, brand, language control and panel geometry as login. Restoring the original login layout supersedes the split-frame presentation: a 1120px desktop grid reserves the same 440px right column for both routes. A shared viewport anchor keeps the cards’ top edges in the same position regardless of registration step height; tall forms grow normally and scroll. Below 1024px both routes share a centered single-column card (maximum 520px), with the small brand inside the card and identical top padding. Its numbered progress indicator describes actual steps, not decorative roles. Long activation instructions use a native disclosure; student/staff ID and name share one row to keep registration compact, stacking only below 360px; password and confirmation remain stacked.
- Authentication forms own validation and focus, preserve editable values on errors and prevent duplicate submission. Registration email remains optional (blank/whitespace submits null), password confirmation compares exact characters, and backend authorization remains authoritative. Passwords, activation/reset codes are masked by default with accessible toggles, kept only in temporary form/component memory, and cleared after successful registration. No credential is put in URLs, logs, analytics or browser storage.
- `auth/login-destination.ts` owns post-authentication destination selection. Ordinary platform-administrator sign-in opens `/platform`. Other accounts use a currently valid server default school, then a valid browser preference, then a valid role-compatible fallback; accounts without a school enter `/practice`. An explicit invitation intent opens the appropriate settings Schools section without automatically opening a modal. Merely returning to `/schools` after sign-out is not invitation intent. School membership and original-school roles remain the authority for every destination.

- Identity deletion is an admin-only, recoverable operation for student/teacher records with no account history. `AdminPeoplePage` owns Active/Deleted lists and feedback; `DeleteIdentityDialog` reuses the maintained `Modal`, `Button` and `Feedback` owners, names the person and ID, starts focus on Cancel, and blocks duplicate/pending dismissal. Deleted records retain their stable ID, number, relationships and Luq ledger. Existing account history (including released bindings) and administrator identities are protected; the drawer explains why. Restore does not reuse old activation codes or grant Luq again. No browser-native confirmation and no direct balance/ledger deletion.

## Do's and Don'ts

Editor follow-up: Escape in the focused code input enables Vim normal mode through the existing settings owner. Normal/visual modes use a full character block with the covered glyph repainted in the theme background color; the block uses `--code-foreground`. Insert mode uses a 3px vertical bar. Forced colors use CanvasText/Canvas. A non-collapsed native text range measures the current character, with one cell for tabs/empty lines; local coordinates account for CSS zoom. The decorative cursor stays clipped to the code viewport and hides on blur or activity read-only state. `FormatCodeIcon` owns the user-selected text-align-start paths for both answer workspaces, with currentColor and the existing toolbar size.

Use existing tokens and sibling controls, not a rebrand. Do not preload or persist locked translations/answers; do not expose reference programs, hidden tests or private notes via ordinary question payloads. Do not reset code or dirty state on theme changes. Scope verification to the touched workflows and record unrelated pre-existing audit findings separately.

Platform governance follow-up (055/056, 2026-11-06): `/platform` is a separate, explicitly authorized administration surface. The initial independent header is superseded by the shared WorkspaceFrame and account-menu settings in the 063 follow-up below. Each school row shows its name, code, aggregate ownership counts and administrators. Actions are create, rename and appoint administrators; the original school retains its existing role management and has no appoint control. No school-suspension or teaching-content placeholder actions. Dialogs reuse Radix and the shared Button/input tokens, focus the first field, retain entered values on error, and prevent pending dismissal or duplicate writes. School names wrap and rows stack on narrow screens. School member lists show an additional administrator label while retaining the linked teacher/student role and hiding member removal for administrators.


School courses follow-up (057, 2026-11-06): `schools/SchoolCourses` owns the current-school course list, search, 50-row paging and student reader. `SchoolCourseEditor` uses the shared Modal/Dialog, Button, field and feedback patterns for metadata and ordered Markdown chapters. Scope is school-wide or selected school classes; teachers select only their assigned classes. Draft edits remain separate from the published version. Publish and unpublish have named confirmations; version conflicts preserve input, require refreshing, and never silently overwrite another editor. Unsaved content prompts before dismissal; pending writes block dismissal and duplicate actions. A student reader uses MathContent, chapter selection plus previous/next controls, and read progress bound to the actual published revision. Unlinked students can read school-wide courses but see why progress is unavailable. No new theme tokens, code editor, problem buttons or public-catalog placeholders. The authority is the 057 section of docs/multischool-workspaces.md; cross-school authorization is always enforced by the domain and database.


Multi-school and public practice follow-up (058–062, 2026-11-06): `schools/PracticePage` uses the shared shell for Home, Courses and Problems. School membership management is now in personal settings rather than a My schools navigation item. Empty catalogs explain that no content is currently published. `PublicCourseReview` and `PublicProblemReview` are explicit platform review surfaces: reviewers inspect the exact published content before granting global access. Course drafts never replace the approved edition. Publishing a different school revision pauses global access until that exact revision is approved again; unpublishing or withdrawal also removes access. Private/class-only courses, hidden tests and teacher reference code are not automatically placed in public payloads.

`PublicPractice` and `SchoolPractice` reuse CodeEditor, MathContent and RunResultPanel for the implemented problem flow. The current public scope is ordinary practice plus course reading/progress, with separate submission context and no old-school points or Scholarship rewards. School course chapters now link to approved school problem versions and formal-AC progress (067 below); global public-course practice linking and assignment/exam/Paper 4 modules remain outside this scope. `/practice/profile` reuses ProfileEditor for avatar/nickname/bio and optional-email/password self-service through `auth/profile`; `/practice/settings` retains appearance/language preferences and joined-school settings. Personal registration creates `identities.kind=personal` credentials without original-school roles; school roles require a scoped invitation, existing identity activation or explicit administrator grant.

Invitation follow-up (062): the existing role select also supports School administrator, explicitly described as authority for this school only. Acceptance never grants original-school `account_roles` or platform administration. Existing original-school activation/role management stays separate. Default interface language remains English; Chinese is an explicit user setting and does not change protected problem content.

Workspace settings and default school follow-up (063, 2026-11-07): platform, original-school, new-school and personal accounts use the same account-menu settings pattern. The Schools section consolidates school details, joining, switching and next-sign-in defaults; neither School settings nor Your schools occupies permanent sidebar space. Explicit invitation links target this section in the current context and do not display a dialog on every login. Platform administrators land in platform administration after ordinary login, including when a school default has been saved.

Migration 063 adds the nullable `accounts.default_school_id` navigation preference. `auth/default-workspace` reads and writes only the signed-in account's preference and validates current school membership or original-school ownership; platform capability alone does not grant school access. Revoked memberships are ignored at read time. Changing this preference does not switch the active workspace; the confirmation states that it applies to the next sign-in. Current-page selection instead prioritizes a valid explicit school ID and the browser's current school before the server default, checking candidates separately so an obsolete choice cannot hide a valid fallback. No school role, student record, grade, code draft or Luq balance is changed by selecting a default.

School identity activation follow-up (064/065, 2026-11-07): `/activate` requires School code before student/staff ID, name and a one-time activation code. Verification and account creation repeat the same server-side school-scoped checks; the preview names the resolved school. A school's administrator issues the code from its unlinked identity row through `SchoolActivationButton`, which displays the school name and slug alongside the temporary secret. No public identity directory or matching-person suggestions are exposed. The original school's existing identity IDs and activation process remain compatible under `legacy-school`; omitted school scope in old clients can only target that original school. Migration 064 adds class archive/revision metadata, and 065 adds school-bound one-time token digests. Activation retains the imported identity and roster rather than duplicating them, while invitation joining remains available to existing accounts.


Workspace refinement follow-up (067, 2026-11-07): Account menus order Profile, Settings, Free practice, Leaderboard (where implemented), Sign out. School workspaces and role/platform switches no longer appear in that dropdown. Personal settings retains joined-school Open/default actions, original-school role choices and the platform-administration entry for authorized accounts. A new-school or personal account is never routed to the original school's leaderboard merely to populate a menu.

`StudentPresenceCard` reuses the 240px online-student popover. Student rows open an in-place recent-activity card rather than a profile URL. Back retains search, page and scroll position; minimize/Escape returns focus to the online trigger. It shows permitted points, solved totals and scholarship plus at most three eligible public first-AC events. Hidden balance fields are omitted by the server; private activity titles, code and hidden tests never enter this response. Presence remains scoped to the original school's implemented service; no fabricated presence or wallet is added for new schools. Chat is deferred because the requested lightweight viewing task does not require messaging, notifications or message moderation.

`SchoolCourses` now follows the original teaching course layout: Import course Markdown/New course actions, Courses/Learning resources tabs, Active/Archived filters and a cover/title/category/chapter/access/status/actions table. The metadata editor and read-only student preview reuse shared controls, covers and Markdown rendering. School resources and chapter problem links remain school-authorized; selected exercises pin published versions and complete through formal AC. Course archive preserves content/history and withdraws access instead of deleting records. Migration 067 adds course metadata snapshots, archive fields and school-scoped learning resources; original-school course records are not converted or overwritten.
