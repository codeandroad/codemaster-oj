# Campus Judge · 设计审查与实现记录

审查对象：`campus-judge-final-design.md` 与现有原型页面。用户已明确将目标改为真实供校内学生使用，并提供 Ubuntu 26.04、4 核 / 8 线程、16GB、Docker、约 200 名学生与每节课 30–50 人的部署条件。

结论：原文可作为界面设计依据，但有生产设计缺口，不能直接按原型的固定结果上线。补充设计见 [生产设计](campus-judge-production-design.md)，部署与验收见 [部署文档](campus-judge-deployment.md)。

| 严重性 | 原设计缺口 | 实现处理 |
| --- | --- | --- |
| P0 | 技术边界禁止鉴权、持久化、真实判题，与学生实际使用目标冲突 | 明确原型/生产两种构建模式；保留预览，生产调用独立 API、数据库与执行器 |
| P0 | 未定义不可信学生代码的隔离、权限和资源边界 | 使用独立 go-judge、非 root 子沙箱、禁网、系统调用过滤和 CPU/内存/进程/输出限制；启动条件不满足则停止 worker |
| P0 | 页面角色切换没有服务端授权契约，隐藏测试可能成为浏览器数据 | 各资源检查拥有者、班级和题库权限；学生 API 不返回正式输入、期望输出、参考代码或私人日志 |
| P1 | 身份名单与登录账号混用，激活、并发认领、解绑、重置缺少事务语义 | 身份 UUID 独立，一次性摘要凭据，原子认领；解绑撤销会话并保留原成绩，重新认领接续历史 |
| P1 | 未规定密码、会话、跨站请求与最后一个管理员的保护 | Argon2id、可撤销服务端会话、Secure/HttpOnly Cookie、Origin/CSRF 检查、登录限流与事务内管理员保护 |
| P1 | 修改题目可能改变旧提交、作业与测试 | 题目版本及已发布测试不可修改；作业、训练和历史提交固定版本 |
| P1 | 自测、自定义输入与正式提交的成绩边界不完整 | 三类任务分开；自定义运行没有正确性分数，自测不进入作业成绩 |
| P1 | 重复点击、断线重试、节点宕机、过期回传没有可靠规则 | 请求去重、数据库任务表、租约与心跳、回传执行编号、平台故障有限重试；故障不计零分 |
| P1 | 作业、计时训练和订正使用何种提交计分不明确 | 作业取截止前有效最高分；训练取个人截止前最后一次正式提交；订正独立且保留原活动成绩 |
| P1 | 倒计时与结果发布缺少服务器规则，预览可能创建真实考试 | 服务端开始/截止、唯一尝试、恢复与延期；教师预览不建立学生尝试，待评测项阻止发布，已发布成绩保存快照 |
| P1 | 函数题参数、返回值、print、签名及不修改输入的要求缺少可执行契约 | 有界 JSON 协议、严格类型比较、签名/异常分类、调用前后参数比较；安全隔离由执行器负责 |
| P1 | 题库/分组与导入文件缺少明确权限及重复确认规则 | 私有/校内题库、教师读/编辑授权、分组只引用同库题目；服务端重新验证导入，题目只进入待验证草稿 |
| P1 | 固定“正常节点”和示例统计不能作为监控与容量证据 | 管理页读取真实队列与运行记录；独立学生会话压测，并明确本地结果不能代替学校硬件验收 |
| P1 | 没有迁移、私有备份、恢复与 HTTPS 部署流程 | 提供 Compose、独立应用/worker 数据库角色、初始化 CLI、预检和数据库备份脚本 |

生产功能和验证以部署文档中的验收记录为准。题目内容、官方比赛资料使用权、校园 HTTPS 域名与学校资料留存策略仍由学校维护；仓库不预填演示账号、固定成绩或假成功结果。
